# Project Definition

## Purpose

This project is a parent-facing vaccine reference for Bulgaria. Its goal is to
answer, in one place, the main practical questions Bulgarian parents have when
deciding how to vaccinate their children, while keeping every answer grounded in
traceable public sources.

The site must also be easy to update when official sources change. New source
versions should be handled through repeatable data or script updates, not
one-off UI edits. Every piece of presented information should remain easy to
trace back to an official source, including the source URL and, where available,
the source date, version, sheet, row, code, or artifact path.

The site should help a parent understand:

- which vaccines are scheduled in Bulgaria and at what ages;
- which vaccines are mandatory and which are recommended;
- which disease or event each vaccine row refers to;
- which Bulgarian, EU, and price registries contain relevant vaccine products;
- how official HIS codes map to product and event names;
- where each fact came from, including source date or version when available;
- what extra detail exists for users who want source-level records.

The project should not try to replace a physician, pharmacist, public health
authority, or product leaflet. It should make official data easier to inspect
and compare.

## Primary Audience

The primary user is a parent in Bulgaria looking for clear vaccine information
for a child. The secondary users are clinicians, pharmacists, journalists, and
technical reviewers who want to inspect the raw source records behind the
parent-facing table.

Design and copy should favor parents first: concise labels, clear grouping,
direct source links, and no unnecessary implementation language in the UI.

## Core User Questions

Every major page or data addition should support at least one of these
questions:

- Schedule: What vaccines are due by age in Bulgaria?
- Requirement: Is this vaccine mandatory or recommended?
- Disease: What disease, condition, or immunization event is this about?
- Product: Which vaccine products exist for this disease/event?
- Registration: Is the product present in Bulgarian or EU medicine registries?
- Price: Is there a Bulgarian price or reimbursement registry entry?
- HIS: Which electronic health system event/product code represents it?
- Source: Which official source says this, and when was that source current?
- Detail: What exact source rows were used if I need to audit the answer?

## Information Architecture

The main navigation is intentionally organized by parent questions:

- `Table`: the readable Bulgarian vaccine schedule.
- `Registries`: product registrations, currently `Bulgarian (BDA)` and
  `EU (EMA)`.
- `Electronic health system (HIS)`: HIS changes, products, and events.
- `Prices (NCPR)`: Bulgarian price/reimbursement registry appendix pages.

The `Details` toggle is for source-level auditing. When it is off, pages should
hide technical columns that do not help most parents. When it is on, pages
should expose old records, technical keys/codes, hidden source columns, and red
source rows where applicable.

When `Details` is off, show only the minimal information of direct interest to
parents. When `Details` is on, show the full available information needed for
source review, auditing, and technical comparison.

## Source Priority

Prefer official, primary sources. Use derived or intermediate files only when
they are generated by repository scripts and preserve a clear link to the
original source.

Current source families:

- Bulgarian immunization ordinance: schedule and legal context.
- HIS nomenclatures: electronic health system products, events, and changes.
- BDA register: Bulgarian medicine registrations.
- EMA medicines report: EU medicine registrations.
- NCPR registers: Bulgarian prices and reimbursement data.
- ECDC and other calendars: comparison links, not Bulgarian source of truth.

When adding a source-backed claim, expose the relevant source link in the UI or
in generated data. If dates, versions, sheet names, or artifact paths are known,
keep them in the generated payload.

Treat traceability as a core data contract. If a transformation filters,
renames, translates, or combines source records, keep enough metadata for a
reviewer to understand which official source rows produced the displayed value.
Avoid changes that make future source refreshes depend on hidden manual steps.

## Data And Build Files

Important files:

- `data/*.yaml`: canonical schedule data, labels, notes, and sources.
- `data/bg/*.yaml`: Bulgarian overlays for matching base data files.
- `data/his/`: HIS workbook artifacts, products, and vaccine specifications.
- `data/bda/`: Bulgarian Drug Agency source and filtered vaccine workbook.
- `data/ema/`: EMA source and filtered J07 vaccine workbook.
- `data/ncpr/vacc/`: filtered NCPR vaccine price workbooks.
- `scripts/build_static_site.py`: builds generated browser data and pages.
- `scripts/filter_ema_atc.py`: filters XLSX workbooks by an ATC prefix column.
- `site-src/`: static HTML, CSS, and client-side renderers.
- `generated-site/`: generated output; rebuild with `make site`.

Run before finishing code or data changes:

```sh
python3 -m py_compile scripts/build_static_site.py
node --check site-src/page-nav.js site-src/app.js site-src/his-sheet.js site-src/ncpr-sheet.js site-src/ema-sheet.js site-src/bda-sheet.js
make site
git diff --check
```

Use narrower checks when a change clearly cannot affect all files, but always
run `make site` after changing source data, site source, or the builder.

## Content Principles

- Keep labels parent-readable: prefer `Product`, `Event`, `ATC`, and plain page
  names over raw source terminology.
- Preserve technical data for audit mode instead of deleting it.
- Avoid unsourced medical interpretation. Explain what a source says; do not
  decide whether an individual child should receive a vaccine.
- Keep Bulgarian and English views aligned. If a source has both Bulgarian and
  English columns, choose the language-specific display value where possible.
- Prefer stable source IDs and generated data fields over ad hoc DOM parsing.
- Do not hide price-related columns on appendix pages, even when details are
  off.
- Keep source text only once on appendix pages; avoid duplicate explanatory
  text after source rows.

## Engineering Principles

- Preserve existing data contracts unless a user-facing requirement needs a
  schema change.
- Keep generated data deterministic and source-traceable.
- Add focused scripts for repeatable filtering/transformation steps rather than
  editing source workbooks manually.
- Design update paths so new source versions can be imported, filtered,
  rebuilt, and reviewed with minimal manual work.
- Do not revert unrelated user changes in a dirty worktree.
- Prefer official source data and generated intermediate files over copying
  values into code.

## Definition Of Done

A change is complete when:

- the user-facing question is answered in the relevant page or data;
- source links and labels remain clear;
- generated pages build without validation errors;
- row counts or filters are verified for workbook transformations;
- the UI has been checked in a browser when layout or navigation changes;
- the final response states what changed and which checks passed.
